# Варианты оптимизаций для дипломного проекта
# Optimization Options for Diploma Project

## Обзор / Overview

Данный документ содержит список возможных оптимизаций для системы распознавания жестов и голосового помощника. Каждый вариант включает описание проблемы, метод оптимизации, ожидаемые результаты и сложность реализации.

This document contains a list of possible optimizations for the gesture recognition and voice assistant system. Each option includes a problem description, optimization method, expected results, and implementation complexity.

---

## Категория 1: Оптимизация производительности компьютерного зрения
## Category 1: Computer Vision Performance Optimization

### 1.1 Оптимизация MediaPipe Hands для реального времени
**Проблема**: MediaPipe Hands может работать медленно на слабых устройствах, особенно при `model_complexity=2` или при обработке двух рук одновременно.

**Метод оптимизации**:
- Динамическая адаптация `model_complexity` в зависимости от FPS
- Использование GPU-ускорения (Metal Performance Shaders на macOS, CUDA на Windows)
- Оптимизация разрешения входного кадра (downscaling перед обработкой, upscaling для отображения)
- Пропуск кадров (frame skipping) при низком FPS
- Кэширование результатов детекции для статичных сцен

**Ожидаемые результаты**:
- Увеличение FPS с 15-20 до 30+ на слабых устройствах
- Снижение задержки (latency) с 100-150ms до 50-70ms
- Снижение энергопотребления на 20-30%

**Сложность**: Средняя (требует профилирования и настройки параметров)

**Метрики для оценки**:
- FPS (кадров в секунду)
- Latency (задержка от кадра до результата)
- CPU/GPU utilization
- Потребление энергии (для ноутбуков)

---

### 1.2 Оптимизация нормализации ландмарков
**Проблема**: Текущая нормализация `wrist_scale` выполняется на каждом кадре, включая вычисление L2-норм для всех 21 точки.

**Метод оптимизации**:
- Векторизация операций с использованием NumPy SIMD
- Кэширование масштабного коэффициента между кадрами (если рука не двигается)
- Использование более быстрых методов нормализации (например, PCA-based normalization)
- Предварительная компиляция нормализации через Numba JIT

**Ожидаемые результаты**:
- Ускорение нормализации в 2-3 раза
- Снижение CPU нагрузки на 5-10%

**Сложность**: Низкая-Средняя

**Метрики**:
- Время выполнения функции `normalize_landmarks()` (микросекунды)
- CPU cycles на операцию

---

### 1.3 Оптимизация обработки видеопотока
**Проблема**: OpenCV захватывает кадры в полном разрешении (1280x720), что избыточно для детекции жестов.

**Метод оптимизации**:
- Многоуровневая обработка: низкое разрешение для детекции (320x240), высокое для отображения
- Асинхронная обработка кадров (threading/async)
- Буферизация кадров с приоритизацией (обрабатывать только последние кадры)
- Использование OpenCV VideoCapture с оптимизированными параметрами

**Ожидаемые результаты**:
- Ускорение обработки на 40-60%
- Снижение использования памяти на 30-40%

**Сложность**: Средняя

**Метрики**:
- FPS обработки
- Использование памяти (MB)
- Latency обработки кадра

## Категория 2: Оптимизация машинного обучения
## Category 2: Machine Learning Optimization

### 2.1 Оптимизация классификатора KNN
**Проблема**: KNN требует вычисления расстояний до всех обучающих примеров при каждом предсказании, что медленно при большом количестве классов/семплов.

**Метод оптимизации**:
- Использование приближенных методов поиска ближайших соседей (Approximate Nearest Neighbors):
  - **FAISS** (Facebook AI Similarity Search) — GPU/CPU ускорение
  - **Annoy** (Spotify) — индексирование для быстрого поиска
  - **HNSW** (Hierarchical Navigable Small World) — графовый метод
- Квантизация признаков (снижение точности float32 → float16 или int8)
- Предварительная фильтрация кандидатов по грубым признакам
- Использование более эффективных метрик расстояния (Manhattan вместо Euclidean для ускорения)

**Ожидаемые результаты**:
- Ускорение инференса в 10-100 раз при большом датасете (1000+ семплов)
- Снижение памяти для хранения модели на 50-75%
- Сохранение точности на уровне 95-98% от исходной

**Сложность**: Средняя-Высокая (требует интеграции новых библиотек)

**Метрики**:
- Время предсказания (миллисекунды)
- Точность классификации (accuracy, precision, recall)
- Размер модели (MB)
- Память при инференсе (MB)

---

### 2.2 Оптимизация обучения модели
**Проблема**: Обучение KNN на большом датасете может занимать много времени, особенно при кросс-валидации и подборе гиперпараметров.

**Метод оптимизации**:
- Параллелизация вычислений расстояний (multiprocessing, joblib)
- Инкрементальное обучение (добавление новых семплов без переобучения всей модели)
- Оптимизация гиперпараметров через Bayesian Optimization (Optuna, Hyperopt)
- Ранняя остановка при достижении целевой точности
- Использование GPU для вычисления расстояний (cuPy, CuPy-based FAISS)

**Ожидаемые результаты**:
- Ускорение обучения в 3-5 раз на многоядерных CPU
- Автоматический подбор оптимальных параметров
- Возможность добавления новых жестов без полного переобучения

**Сложность**: Средняя

**Метрики**:
- Время обучения (секунды)
- Точность на валидационной выборке
- Количество итераций оптимизации

---

### 2.3 Оптимизация извлечения признаков
**Проблема**: Текущий метод усреднения признаков по времени теряет временную информацию, что снижает точность для динамических жестов.

**Метод оптимизации**:
- Использование временных признаков (LSTM/GRU) для последовательностей жестов
- Извлечение статистических признаков (mean, std, min, max, median) вместо простого усреднения
- Применение PCA для снижения размерности признаков
- Использование автоэнкодеров для сжатия признаков
- Временные окна с перекрытием (sliding window) для более плавного распознавания

**Ожидаемые результаты**:
- Увеличение точности распознавания на 5-15%
- Снижение размерности признаков на 30-50% при сохранении информативности
- Лучшее распознавание динамических жестов

**Сложность**: Высокая (требует изменения архитектуры)

**Метрики**:
- Точность классификации
- Размерность признаков
- Время извлечения признаков

---

### 2.4 Замена KNN на более эффективные модели
**Проблема**: KNN не масштабируется на большие датасеты и требует хранения всех обучающих примеров.

**Метод оптимизации**:
- **SVM (Support Vector Machine)** с RBF kernel — быстрый инференс, компактная модель
- **Random Forest** — ансамбль деревьев, быстрый предсказания
- **LightGBM / XGBoost** — градиентный бустинг, высокая точность и скорость
- **Нейронные сети** (маленький MLP) — быстрый инференс после обучения
- **Квантизованные модели** (TensorFlow Lite, ONNX Runtime) — оптимизация для мобильных устройств

**Ожидаемые результаты**:
- Ускорение инференса в 5-20 раз
- Снижение размера модели на 60-80%
- Улучшение точности на 2-5%

**Сложность**: Средняя-Высокая (требует переписывания pipeline обучения)

**Метрики**:
- Время инференса
- Размер модели
- Точность
- Память при инференсе

---

## Категория 3: Оптимизация базы данных
## Category 3: Database Optimization

### 3.1 Оптимизация запросов PostgreSQL
**Проблема**: При большом количестве команд и истории жестов запросы могут выполняться медленно.

**Метод оптимизации**:
- Создание индексов на часто используемых полях:
  - `commands.gesture_id` (FK)
  - `gesture_history.executed_at` (для временных запросов)
  - `gestures.label` (для поиска по имени)
  - `commands.name` (для поиска команд)
- Партиционирование таблицы `gesture_history` по датам (ежемесячные партиции)
- Использование материализованных представлений для статистики
- Кэширование часто запрашиваемых данных в памяти (Redis, in-memory cache)
- Оптимизация JOIN-запросов через EXPLAIN ANALYZE

**Ожидаемые результаты**:
- Ускорение запросов в 10-100 раз
- Снижение нагрузки на БД на 30-50%
- Масштабируемость до миллионов записей

**Сложность**: Средняя

**Метрики**:
- Время выполнения запросов (миллисекунды)
- Размер индексов (MB)
- CPU/IO нагрузка БД

---

### 3.2 Оптимизация встраиваемой PostgreSQL (pg_embed)
**Проблема**: pg_embed может занимать много места на диске и медленно запускаться.

**Метод оптимизации**:
- Настройка параметров PostgreSQL для embedded использования:
  - `shared_buffers` — оптимизация под доступную память
  - `work_mem` — для сортировок и JOIN
  - `maintenance_work_mem` — для создания индексов
  - `checkpoint_segments` — для снижения нагрузки на диск
- Использование WAL (Write-Ahead Logging) для быстрой записи
- Автоматическая очистка старых записей истории (TTL)
- Сжатие данных через TOAST (автоматически в PostgreSQL)

**Ожидаемые результаты**:
- Ускорение запуска БД с 2-3 секунд до <1 секунды
- Снижение размера БД на 20-40%
- Улучшение производительности записи на 30-50%

**Сложность**: Низкая-Средняя

**Метрики**:
- Время запуска БД (секунды)
- Размер БД на диске (MB)
- Время выполнения INSERT/UPDATE (миллисекунды)

---

### 3.3 Оптимизация работы с SQLAlchemy ORM
**Проблема**: ORM может генерировать неоптимальные SQL-запросы и создавать N+1 проблемы.

**Метод оптимизации**:
- Использование `joinedload()` и `selectinload()` для eager loading связей
- Батчинг операций (bulk insert/update)
- Использование raw SQL для сложных запросов
- Кэширование сессий и объектов через `expire_on_commit=False`
- Использование connection pooling с оптимальными параметрами

**Ожидаемые результаты**:
- Ускорение запросов в 2-5 раз
- Снижение количества SQL-запросов на 50-70%

**Сложность**: Средняя

**Метрики**:
- Количество SQL-запросов на операцию
- Время выполнения запросов
- Использование памяти ORM

---

## Категория 4: Оптимизация пользовательского интерфейса
## Category 4: User Interface Optimization

### 4.1 Оптимизация рендеринга QML
**Проблема**: QML может тормозить при сложных анимациях и частых обновлениях UI.

**Метод оптимизации**:
- Использование `ListView` с делегатами вместо множества отдельных элементов
- Ленивая загрузка компонентов (lazy loading)
- Оптимизация анимаций через `PropertyAnimation` с `easing`
- Использование `Canvas` для кастомной отрисовки вместо множества элементов
- Кэширование изображений и ресурсов
- Отключение обновлений UI при невидимых панелях

**Ожидаемые результаты**:
- Увеличение FPS UI с 30 до 60
- Снижение использования CPU на 20-30%
- Плавные анимации без лагов

**Сложность**: Средняя

**Метрики**:
- FPS рендеринга UI
- CPU использование UI-потока
- Время отрисовки кадра (миллисекунды)

---

### 4.2 Оптимизация отображения видеопотока в QML
**Проблема**: Отображение кадров с камеры в QML может быть медленным из-за конвертации форматов.

**Метод оптимизации**:
- Использование `QQuickImageProvider` для прямой передачи кадров
- Конвертация кадров в QML-совместимый формат в отдельном потоке
- Использование OpenGL для аппаратного ускорения отрисовки
- Снижение частоты обновления UI (не каждый кадр, а каждый N-й)
- Использование `QVideoSink` для прямого вывода видео

**Ожидаемые результаты**:
- Снижение задержки отображения с 100ms до 30-50ms
- Снижение нагрузки на CPU на 15-25%

**Сложность**: Высокая (требует работы с Qt Multimedia)

**Метрики**:
- Latency отображения кадра
- CPU использование
- FPS отображения

---

### 4.3 Оптимизация реактивности UI
**Проблема**: UI может "зависать" при выполнении тяжелых операций (обучение модели, загрузка данных).

**Метод оптимизации**:
- Вынос тяжелых операций в отдельные потоки (QThread, QRunnable)
- Использование `QFuture` и `QtConcurrent` для асинхронных операций
- Показ прогресс-баров и индикаторов загрузки
- Отмена длительных операций через сигналы
- Использование `QQuickAsyncImageProvider` для асинхронной загрузки изображений

**Ожидаемые результаты**:
- UI остается отзывчивым даже при тяжелых операциях
- Улучшение пользовательского опыта

**Сложность**: Средняя

**Метрики**:
- Время отклика UI на действия пользователя (миллисекунды)
- Количество "зависаний" UI

---

## Категория 5: Оптимизация голосового помощника
## Category 5: Voice Assistant Optimization

### 5.1 Оптимизация Text-to-Speech (TTS)
**Проблема**: TTS может быть медленным и потреблять много ресурсов, особенно при использовании нейросетевых моделей.

**Метод оптимизации**:
- Кэширование озвученных фраз (сохранение аудио в файлы)
- Использование более быстрых TTS движков (pyttsx3 вместо Coqui TTS для простых фраз)
- Предварительная генерация часто используемых фраз
- Асинхронное озвучивание (не блокировать основной поток)
- Оптимизация параметров голоса (скорость, pitch) для баланса качества/скорости

**Ожидаемые результаты**:
- Снижение задержки TTS с 500-1000ms до 50-200ms (при кэшировании)
- Снижение использования CPU на 40-60%

**Сложность**: Низкая-Средняя

**Метрики**:
- Время генерации речи (миллисекунды)
- Размер кэша TTS (MB)
- CPU использование TTS

---

### 5.2 Оптимизация Speech-to-Text (STT)
**Проблема**: Распознавание речи может быть медленным, особенно при использовании облачных API или тяжелых локальных моделей.

**Метод оптимизации**:
- Использование легковесных локальных моделей (Vosk small вместо large)
- Квантизация моделей STT (int8 вместо float32)
- Предварительная фильтрация тишины (VAD - Voice Activity Detection)
- Использование streaming recognition вместо batch
- Кэширование часто распознаваемых команд

**Ожидаемые результаты**:
- Ускорение распознавания в 2-3 раза
- Снижение размера модели на 50-70%
- Снижение ложных срабатываний на 30-40%

**Сложность**: Средняя

**Метрики**:
- Время распознавания (секунды)
- Точность распознавания (%)
- Размер модели STT (MB)

---

## Категория 6: Оптимизация памяти и ресурсов
## Category 6: Memory and Resource Optimization

### 6.1 Оптимизация использования памяти
**Проблема**: Приложение может потреблять много памяти из-за буферизации кадров, моделей ML, и данных БД.

**Метод оптимизации**:
- Ограничение размера буферов кадров (deque с maxlen)
- Ленивая загрузка моделей ML (загружать только при необходимости)
- Очистка неиспользуемых данных из памяти (garbage collection tuning)
- Использование генераторов вместо списков для больших датасетов
- Оптимизация форматов данных (np.float32 вместо np.float64 где возможно)

**Ожидаемые результаты**:
- Снижение использования памяти на 30-50%
- Улучшение стабильности на слабых устройствах

**Сложность**: Низкая-Средняя

**Метрики**:
- Использование памяти (MB)
- Пиковое использование памяти
- Утечки памяти (через memory profiler)

---

### 6.2 Оптимизация энергопотребления
**Проблема**: Постоянная обработка видео и ML может быстро разряжать батарею ноутбука.

**Метод оптимизации**:
- Адаптивная частота обработки (снижать FPS при отсутствии активности)
- Переход в "спящий режим" при отсутствии рук в кадре
- Использование энергоэффективных алгоритмов (более простые модели при работе от батареи)
- Оптимизация использования CPU/GPU (снижение нагрузки при низком заряде)
- Мониторинг уровня заряда и предупреждение пользователя

**Ожидаемые результаты**:
- Увеличение времени работы от батареи на 30-50%
- Снижение нагрева устройства

**Сложность**: Средняя

**Метрики**:
- Время работы от батареи (часы)
- Потребление энергии (Вт)
- Температура CPU/GPU

---

## Категория 7: Оптимизация точности распознавания
## Category 7: Recognition Accuracy Optimization

### 7.1 Оптимизация сглаживания предсказаний
**Проблема**: Текущее скользящее окно может давать неточные результаты при быстрых жестах или при переключении между жестами.

**Метод оптимизации**:
- Использование взвешенного усреднения (больший вес последним кадрам)
- Применение фильтра Калмана для сглаживания предсказаний
- Использование временных моделей (LSTM) для учета последовательности
- Адаптивный размер окна в зависимости от скорости жеста
- Использование confidence scores для фильтрации неуверенных предсказаний

**Ожидаемые результаты**:
- Увеличение точности распознавания на 5-10%
- Снижение ложных срабатываний на 20-30%
- Более плавное переключение между жестами

**Сложность**: Средняя-Высокая

**Метрики**:
- Accuracy (точность)
- Precision (точность положительных предсказаний)
- Recall (полнота)
- F1-score
- Количество ложных срабатываний

---

### 7.2 Оптимизация обработки edge cases
**Проблема**: Система может неправильно распознавать жесты при плохом освещении, частичном перекрытии руки, или при быстрых движениях.

**Метод оптимизации**:
- Адаптивная нормализация в зависимости от качества детекции
- Использование нескольких кадров для восстановления пропущенных ландмарков
- Фильтрация выбросов (outlier detection) в признаках
- Использование ансамбля моделей для повышения надежности
- Адаптивные пороги confidence в зависимости от условий

**Ожидаемые результаты**:
- Улучшение точности в сложных условиях на 10-20%
- Снижение количества "не распознано" на 30-40%

**Сложность**: Высокая

**Метрики**:
- Accuracy в различных условиях (освещение, угол камеры)
- Количество "не распознано" случаев
- Robustness score

## Категория 8: Оптимизация архитектуры и кода
## Category 8: Architecture and Code Optimization

### 8.1 Оптимизация многопоточности
**Проблема**: Текущая архитектура может быть неоптимальной для параллельной обработки.

**Метод оптимизации**:
- Разделение потоков: захват видео, обработка CV, ML инференс, UI обновление
- Использование thread pool для параллельной обработки нескольких жестов
- Асинхронная архитектура с asyncio для I/O операций
- Использование очередей (queue.Queue) для передачи данных между потоками
- Оптимизация блокировок (lock-free структуры данных где возможно)

**Ожидаемые результаты**:
- Улучшение общей производительности на 20-40%
- Лучшая утилизация многоядерных CPU
- Снижение задержек

**Сложность**: Высокая (требует рефакторинга)

**Метрики**:
- CPU utilization по потокам
- Throughput (обработанных кадров в секунду)
- Latency между компонентами

### 8.2 Оптимизация импортов и загрузки модулей
**Проблема**: Медленный старт приложения из-за загрузки тяжелых библиотек (MediaPipe, PySide6, ML модели).

**Метод оптимизации**:
- Ленивая загрузка модулей (импорт только при необходимости)
- Предзагрузка критических модулей в фоне
- Использование `__import__()` для динамических импортов
- Оптимизация порядка импортов
- Кэширование байткода Python (.pyc файлы)

**Ожидаемые результаты**:
- Ускорение запуска приложения с 3-5 секунд до 1-2 секунд
- Снижение использования памяти при старте на 20-30%

**Сложность**: Низкая

**Метрики**:
- Время запуска приложения (секунды)
- Время до первого отображения UI
- Использование памяти при старте
